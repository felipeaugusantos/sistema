-DESCRIÇÃO DAS NECESSIDADES DO CLIENTE OU SISTEMA:

  O REPOR+ (PRODUTO NOVO EM FLUTTER) TAMBÉM TRABALHA COM COTAÇÃO DE COMPRA E JÁ REALIZA A
  CRIAÇÃO E A MANUTENÇÃO DA COTAÇÃO. A TELA "ADICIONAR PRODUTOS VIA GIRO" PRECISA DA SUGESTÃO
  DE ITENS DE COMPRA CALCULADA POR GIRO DE ESTOQUE — REGRA CONSOLIDADA NO AUTCOM E JÁ
  COMPARTILHADA ENTRE PEDIDO DE COMPRA E COTAÇÃO.

  PARA QUE O RESULTADO SEJA IDÊNTICO NOS DOIS PRODUTOS E A REGRA CONTINUE COM UM ÚNICO DONO, O
  CÁLCULO PERMANECE ONDE ESTÁ E PASSA A SER EXPOSTO VIA REST. A SUPRIMENTO.SERVICES.API EXERCE
  PARA COTAÇÃO O MESMO PAPEL QUE A FATURAMENTO.SERVICES.API JÁ EXERCE PARA VENDAS: ATENDER O
  BACKEND JAVA COM UMA REGRA DE NEGÓCIO EXISTENTE, EVITANDO DUPLICAÇÃO DE LÓGICA.

  O CÁLCULO DE GIRO É PESADO E PODE LEVAR VÁRIOS MINUTOS. O USUÁRIO NÃO PODE FICAR PRESO NA
  TELA ESPERANDO: DEVE DISPARAR A GERAÇÃO, CONTINUAR USANDO O SISTEMA E SER AVISADO QUANDO O
  RESULTADO ESTIVER PRONTO.


-RESUMO DO FLUXO:

  1. REPOR+ CHAMA A API COM O RASCUNHO DA COTAÇÃO E OS FILTROS DE GIRO NO BODY, E A EMPRESA E O
     OPERADOR LOGADO NOS HEADERS
  2. A API GRAVA UMA LINHA DE TAREFA NA SSATSK
  3. A API DISPARA UM PROCESSO SEPARADO DO PRÓPRIO SUPRIMENTOSERVICESAPI, EM MODO NOVO "TASK",
     SÓ PARA EXECUTAR AQUELA TAREFA
  4. A API RESPONDE HTTP 202 NA HORA, DEVOLVENDO O IDENTIFICADOR DO PROCESSAMENTO
  5. O PROCESSO SEPARADO CALCULA O GIRO, GRAVA OS ITENS NO RASCUNHO, ENCERRA A LINHA DA TAREFA
     E GRAVA A NOTIFICAÇÃO DE CONCLUSÃO
  6. O REPOR+ RECEBE A NOTIFICAÇÃO, REVISA OS ITENS, PERMITE INCLUSÃO MANUAL E PROMOVE O
     RASCUNHO PARA A COTAÇÃO OFICIAL POR CONTA PRÓPRIA

  O PROCESSO SEPARADO É INDEPENDENTE DA API. REINICIAR O SERVIÇO NÃO INTERROMPE UM GIRO EM
  ANDAMENTO, E UM GIRO LONGO NÃO OCUPA WORKER DO POOL SÍNCRONO.

      (SERVICES.CORE.WORKER.PAS LINHAS 546-555, CREATEWORKER): SHELLEXECUTE COM COMANDO EM

      GRAVADO EM ARQUIVO, REDIRECIONANDO SAÍDA PARA LOG PRÓPRIO DA TAREFA.

      * VALIDAR QUE O ID É NUMÉRICO ANTES DE CONCATENAR NO COMANDO DE SHELL. O VALOR VEM DE

      * NÃO PASSAR PELO POOL DE WORKERS E NÃO ALTERAR O PROTOCOLO DO POOL. NO ONEXECUTE

[ 5 ] COLUNAS NOVAS NA SSATSK

      A SSATSK CONTINUA SENDO A TABELA DE TAREFAS. NÃO CRIAR TABELA DE CONTROLE NOVA. ELA JÁ
      GRAVA PARAMS, EMPRESA, INÍCIO, FIM, SUCESSO, TIPO DE ERRO E MENSAGEM, E AS LINHAS NÃO
      SÃO APAGADAS APÓS A LEITURA DO RESULTADO.

      ESTRUTURA ATUAL, PARA REFERÊNCIA:

        AUTOINCREM  BIGINT        NO   PRI  AUTO_INCREMENT
        SST_DTAINS  DATETIME      YES  MUL
        SST_SERVIC  VARCHAR(255)  YES
        SST_METHOD  VARCHAR(255)  YES
        SST_PARAMS  LONGTEXT      YES
        SST_CODEMP  CHAR(3)       YES
        SST_DTAINI  DATETIME      YES
        SST_DTAFIN  DATETIME      YES
        SST_SUCESS  CHAR(1)       YES  DEFAULT 'N'
        SST_RESULT  LONGTEXT      YES
        SST_TYPERR  VARCHAR(255)  YES

      ACRESCENTAR TRÊS COLUNAS, SEGUINDO O PADRÃO DA TABELA — PREFIXO SST_ MAIS SEIS LETRAS,
      TODAS NULÁVEIS PARA NÃO AFETAR AS LINHAS EXISTENTES:

        SST_ASSINC  CHAR(1)   YES  DEFAULT 'N'   'S' = TAREFA ASSÍNCRONA
        SST_CODOPE  CHAR(3)   YES                OPERADOR QUE SOLICITOU A TAREFA
        SST_STATUS  LONGTEXT  YES                PROGRESSO DA TAREFA, EM JSON

      O SST_STATUS SUBSTITUI TRÊS COLUNAS QUE ESTE REQUISITO IA CRIAR — ETAPA, POSIÇÃO E TOTAL.
      FORMATO, IGUAL AO QUE O GET DEVOLVE:

        {"etapa":"Calculando giro...","progresso":{"posicao":120,"total":1881}}

      * O CRITÉRIO PARA UM CAMPO SER COLUNA OU ENTRAR NO JSON NÃO É GOSTO: **É SE ELE APARECE EM
        WHERE.** SST_ASSINC E SST_CODOPE FICAM COLUNA; ETAPA E PROGRESSO ENTRAM NO JSON. ESSA
        REGRA PRECISA SER RESPEITADA PELO PRÓXIMO CONSUMIDOR — SEM ELA O CAMPO VIRA DEPÓSITO, E
        SEIS MESES DEPOIS ALGUÉM PRECISA FILTRAR POR ALGO QUE ESTÁ LÁ DENTRO. *

      * MOTIVO DE AGRUPAR — ETAPA, POSIÇÃO E TOTAL SÃO UM DADO COESO: NENHUM DOS TRÊS SIGNIFICA
        NADA SOZINHO. E SÃO WRITE-MOSTLY / READ-BY-KEY: NADA FILTRA NEM AGREGA POR ELES, SÓ O GET
        LÊ A LINHA PELO ID. É EXATAMENTE O CASO EM QUE JSON É SEGURO. *

      * MOTIVO QUE PESA MAIS QUE ESTE REQUISITO — A SSATSK É SERVIDA POR TRÊS SERVIÇOS. O PRÓXIMO
        CONSUMIDOR DE TAREFA ASSÍNCRONA VAI QUERER SUB-ETAPA, CONTADOR DE TENTATIVAS OU PARCIAL
        DE ITENS. COM O JSON, ENTRA SEM DDL. SEM ELE, CADA CONSUMIDOR PEDE COLUNA PRÓPRIA, E É
        ASSIM QUE SE CHEGA A UMA TABELA COM DEZENAS DE COLUNAS EM QUE A MAIORIA É NULL. *

      * NÃO É INVENÇÃO NESTA TABELA, É SIMETRIA COM O QUE JÁ EXISTE: O SST_PARAMS JÁ É JSON EM
        LONGTEXT (SERVICES.CORE.WORKER.PAS LINHA 848, FEXECUTETASK, FORMATJSON). LOGO
        SST_PARAMS É A ENTRADA DA
        TAREFA E SST_STATUS É A SAÍDA. *

      * LONGTEXT E NÃO O TIPO JSON NATIVO, PARA ACOMPANHAR O SST_PARAMS E NÃO CRIAR DEPENDÊNCIA
        DE VERSÃO DO MYSQL — HÁ CLIENTE EM 5.7 E EM 8.0. *

      * CUSTO A ACEITAR: CADA ATUALIZAÇÃO DE PROGRESSO REESCREVE O DOCUMENTO INTEIRO, EM VEZ DE
        DOIS INTEIROS. COM O THROTTLE DO BLOCO [ 8 ] É IRRELEVANTE; SEM ELE SERIA PIOR QUE
        COLUNAS. OU SEJA, O JSON TORNA O THROTTLE OBRIGATÓRIO DE FATO, NÃO RECOMENDADO. *

      * A FORMA ARMAZENADA É A MESMA DA RESPOSTA DO GET, ENTÃO O ENDPOINT QUASE REPASSA — SÓ
        ACRESCENTA O PERCENTUAL CALCULADO. NÃO CRIAR UM SEGUNDO FORMATO SÓ PARA O BANCO. *

      * NÃO EXISTE COLUNA COM O RASCUNHO ALVO, E ISSO É DELIBERADO. A PERGUNTA "EXISTE GIRO
        RODANDO PARA ESTE RASCUNHO?" É RESPONDIDA PELO ADVISORY LOCK NOMEADO PELO PRÓPRIO
        RASCUNHO — IS_USED_LOCK('COTGIRO:COTRES_<SEQ>') — SEM CONSULTAR TABELA NENHUMA, O QUE É
        MAIS BARATO QUE CONSULTAR POR COLUNA INDEXADA. VER BLOCO [ 13 ]. *

      * A VARREDURA DE ÓRFÃS PRECISA RECONSTRUIR O NOME DO LOCK A PARTIR DA LINHA, E PARA ISSO LÊ
        O SEQRASCUNHO DO SST_PARAMS. É ACEITÁVEL PORQUE É JOB DE SEGUNDO PLANO SOBRE POUCAS
        LINHAS EM ABERTO — O CUSTO QUE PRECISA SER EVITADO É NO CAMINHO DO REQUEST. *

      * O PROCESSO DA TAREFA JÁ LÊ O SST_PARAMS DE QUALQUER FORMA: É DALI QUE SAI O SEQRASCUNHO
        QUE DIZ O QUE CALCULAR. LOGO O RASCUNHO JÁ ESTÁ DISPONÍVEL EM TODO LUGAR QUE LÊ PARAMS,
        INCLUSIVE NA GRAVAÇÃO DA NOTIFICAÇÃO DO BLOCO [ 12 ]. *

      * SST_ASSINC EXISTE PARA QUE A CONSULTA DO 409, O TETO DE PROCESSOS E A VARREDURA DE
        ÓRFÃS SEJAM INEQUÍVOCOS. IDENTIFICAR TAREFA ASSÍNCRONA PELO NOME DO SERVIC OU DO
        METHOD FUNCIONA HOJE E QUEBRA NO SEGUNDO CONSUMIDOR DO MODELO. *

      * SST_CODOPE É COLUNA, E NÃO CAMPO DENTRO DO SST_PARAMS, PORQUE SEGUE A CONVENÇÃO JÁ
        ESTABELECIDA: CONTEXTO DE EXECUÇÃO MORA EM COLUNA, PARÂMETRO DE NEGÓCIO MORA NO
        SST_PARAMS. A EMPRESA JÁ FAZ ASSIM — É GRAVADA EM SST_CODEMP
        (SERVICES.CORE.WORKER.PAS LINHA 849, FEXECUTETASK) E AINDA VIAJA UMA SEGUNDA VEZ
        COMO -E NA LINHA DE
        COMANDO DO PROCESSO (LINHA 551), NUNCA DENTRO DO SST_PARAMS. O MESMO VALE PARA O
        SSA_CODEMP DO SERVIÇO DE FATURAMENTO. OPERADOR É DA MESMA NATUREZA QUE EMPRESA. *
